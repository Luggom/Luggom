## Validadores externos — o que fazer

### 1. Descarregar e verificar

Descarrega da release:
<https://github.com/Luggom/Luggom/releases/tag/testnet-2026-11-17>

- `luggomd` (SHA256 acima);
- `genesis-draft.json` (SHA256 acima).

```sh
sha256sum luggomd genesis-draft.json
luggomd version --long --output json   # testnet-2026-11-17 / 7fa7dfc
```

### 2. Backup

```sh
cp ~/.luggom/config/priv_validator_key.json ~/priv_validator_key.json.bak
cp ~/.luggom/config/node_key.json ~/node_key.json.bak
```

Guarda o `priv_validator_key.json`: o gentx tem de usar a **mesma chave de
consenso** com que vais correr. Não a regeneres.

### 3. Colocar o genesis draft

```sh
cp ~/.luggom/config/genesis.json ~/.luggom/config/genesis.luggom-test.json.bak
cp genesis-draft.json ~/.luggom/config/genesis.json
```

### 4. Criar o gentx

```sh
luggomd genesis gentx <a-tua-chave> 200000000000000000000uluggom \
  --chain-id luggom-test01 \
  --home ~/.luggom \
  --keyring-backend <test|file|os> \
  --commission-rate 0.10 --commission-max-rate 0.20 --commission-max-change-rate 0.01
```

A conta já está fundada no draft; não envias fundos.

Confirma que a pubkey do gentx é a chave com que vais correr:

```sh
luggomd comet show-validator --home ~/.luggom
```

### 5. Enviar o gentx

Envia `~/.luggom/config/gentx/gentx-*.json` ao coordenador (grupo do Telegram ou
endereço publicado na release) até **2026-11-16 02:00 UTC**.

**Não** corras `collect-gentxs`. O coordenador recolhe os 16 e publica o genesis
final.

### 6. Esperar pelo genesis final

O `genesis.json` final (com 16 gentxs) é publicado até **2026-11-16 12:00 UTC** na
mesma release. O SHA256 é publicado lá e no grupo.

### 7. Reset e arranque

Às **2026-11-17 02:00 UTC**:

```sh
sudo systemctl stop <a-tua-unit-luggom>
cp genesis.json ~/.luggom/config/genesis.json
luggomd comet unsafe-reset-all --home ~/.luggom
sed -i 's/^chain-id = .*/chain-id = "luggom-test01"/' ~/.luggom/config/client.toml
luggomd start --home ~/.luggom
```

- `persistent_peers` pode incluir o seed público:
  `1530baa7b3a07e0cab8dc81c9c08fccc51a47471@62.146.183.122:26656`
- Se ligares por IP, põe `addr_book_strict = false` no `config.toml`.
- **Sem state-sync no bloco 0.** Os validadores de genesis arrancam do genesis; os
  `trust_height`/`trust_hash` antigos estão obsoletos. State-sync só faz sentido
  para quem entrar depois de existirem snapshots.

### 8. Verificar

```sh
curl -s http://127.0.0.1:26657/status   # catching_up: false, altura a subir
luggomd query staking validators --node tcp://127.0.0.1:26657
```

Devem aparecer **16 validadores**, todos `BOND_STATUS_BONDED`, e o teu nó a
assinar. Publica no grupo o teu endereço `luggom1…`, o moniker e
`catching_up: false`.

## Chain antiga e quórum

- A `luggom-test` é abandonada. Para o nó antigo no momento do reset; não reinicies
  o binário antigo nem continues a produzir a chain antiga.
- A chain nova precisa de **11 de 16** validadores online. Se mais de 5 não
  atualizarem, a nova chain não arranca.
- O LUG de testnet não tem valor; a chain pode ser resetada.
